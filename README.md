# Tutor RAG

AI-powered assistant for tutors, built with Python, FastAPI, PostgreSQL and Retrieval-Augmented Generation (RAG).

## 1. О проекте

**Tutor RAG** — сервис для управления контекстом обучения учеников с помощью LLM и RAG.

Система хранит информацию об учениках, проведённых занятиях, домашних заданиях, пройденных темах и трудностях в обучении.

Вместо ручного поиска по заметкам репетитор может задавать вопросы на естественном языке:

- «Что мы проходили с учеником на последних трёх занятиях?»
- «Какие темы вызывают у него наибольшие трудности?»
- «Какое домашнее задание было задано?»
- «Что стоит повторить на следующем занятии?»
- «Составь краткий бриф перед следующим уроком».

**Основной принцип:** данные об учениках принадлежат пользователю и хранятся в собственной базе данных. Внешние сервисы используются только для интеграций и LLM, когда выбран облачный провайдер.

## 2. MVP

Первая версия представляет собой backend-сервис с REST API и Swagger UI.

### Основные возможности

**Управление учениками**

- Создание, получение, редактирование и удаление учеников.
- Хранение обезличенного идентификатора, уровня подготовки и учебных целей.
- Получение списка учеников.

**Управление занятиями**

- Добавление проведённого занятия.
- Сохранение даты, темы, заметок, домашнего задания и выявленных трудностей.
- Получение истории занятий конкретного ученика.

**RAG**

- Индексация текстовых заметок занятий.
- Генерация embeddings.
- Semantic Search по истории занятий.
- Фильтрация контекста по ученику до передачи в LLM.
- Генерация ответа с использованием найденных данных.
- Возврат источников, на которых основан ответ.

**LLM**

- Поддержка облачного LLM API.
- Поддержка локальных моделей через Ollama.
- Возможность переключения провайдера через конфигурацию.

**Интерфейс**

- Swagger UI (`/docs`).
- REST API для управления данными и запросов к RAG.
- Загрузка начальных данных через JSON.

### Что не входит в MVP

- Полноценный frontend.
- Авторизация нескольких пользователей.
- Интеграция с календарём.
- Автоматические уведомления.
- Голосовые заметки и транскрипция.
- AI-агенты и сложные workflow.
- Платежи, CRM и полноценная LMS.

## 3. Технологический стек

| Компонент | Технология | Назначение |
|---|---|---|
| Язык | Python 3.14 | Backend |
| API | FastAPI | REST API и Swagger |
| Валидация | Pydantic v2 | DTO и схемы |
| ORM | SQLAlchemy 2 | Работа с БД |
| Миграции | Alembic | Версионирование схемы |
| База данных | PostgreSQL 17 | Хранение данных |
| Vector Search | pgvector | Поиск по embeddings |
| LLM | Cloud API / Ollama | Генерация ответов |
| RAG | LangChain | Интеграция компонентов RAG |
| HTTP Client | httpx | Внешние API |
| Конфигурация | pydantic-settings | Переменные окружения |
| Тестирование | pytest | Unit и integration tests |
| Инфраструктура | Docker Compose | Локальный запуск |

**Примечание:** LangChain используется как вспомогательная библиотека, а не как основа всей бизнес-логики. Компоненты LLM, embeddings и retrieval должны быть заменяемыми.

### Архитектурные принципы

- Разделение HTTP, бизнес-логики и доступа к данным.
- Dependency Injection через FastAPI `Depends`.
- Асинхронная работа с PostgreSQL.
- Изоляция провайдеров LLM и embeddings.
- Фильтрация данных по `student_id`.
- Сохранение источников ответов.
- Отсутствие прямой зависимости бизнес-логики от LangChain.

## 7. Как работает RAG

### Индексация

1. Репетитор создаёт или обновляет запись о занятии.
2. Система формирует текст для индексации.
3. Текст разбивается на фрагменты при необходимости.
4. Embedding-модель создаёт векторы.
5. Фрагменты и векторы сохраняются в PostgreSQL с pgvector.

### Генерация ответа

1. Пользователь отправляет вопрос.
2. Система определяет область поиска — конкретного ученика.
3. Вопрос преобразуется в embedding.
4. pgvector находит релевантные фрагменты.
5. Система собирает контекст с указанием источников.
6. Контекст и вопрос передаются выбранной LLM.
7. API возвращает ответ и ссылки на исходные записи.

Пример запроса:

```http
POST /api/chat/query
Content-Type: application/json
```

```json
{
  "student_id": "student-uuid",
  "question": "Какие темы нужно повторить?"
}
```

Пример ответа:

```json
{
  "answer": "Рекомендуется повторить квадратные уравнения.",
  "sources": [
    {
      "lesson_id": "lesson-uuid",
      "excerpt": "Возникли трудности с дискриминантом."
    }
  ]
}
```

## 9. Конфигурация

Пример `.env.example`:

```dotenv
POSTGRES_USER=tutor
POSTGRES_PASSWORD=change_me
POSTGRES_DB=tutor_rag

DATABASE_URL=postgresql+asyncpg://tutor:change_me@db:5432/tutor_rag

LLM_PROVIDER=ollama
LLM_MODEL=your-model
OLLAMA_BASE_URL=http://host.docker.internal:11434

EMBEDDING_PROVIDER=ollama
EMBEDDING_MODEL=your-embedding-model

# Для облачного провайдера
LLM_API_KEY=
```

LLM и embedding-модели конфигурируются отдельно. При смене embedding-модели может потребоваться переиндексация данных.

Адрес Ollama зависит от среды запуска и должен быть настроен для конкретной Docker-конфигурации.

## 10. Локальный запуск

Предполагается запуск FastAPI и PostgreSQL через Docker Compose.

```bash
cp .env.example .env
docker compose up --build -d
```

После запуска:

- Swagger UI: `http://localhost:8000/docs`
- OpenAPI: `http://localhost:8000/openapi.json`
- Health: `http://localhost:8000/health`

Миграции базы данных выполняются через Alembic.

```bash
docker compose exec api alembic upgrade head
```

Команды являются целевым интерфейсом проекта и будут работать после реализации соответствующей конфигурации.

## 12. Безопасность и приватность

- Персональные данные учеников не должны включаться в RAG-контекст без необходимости.
- Для работы с LLM используются обезличенные идентификаторы.
- Доступ к данным ограничивается на уровне приложения и запросов к БД.
- Перед отправкой контекста в LLM выполняется фильтрация по ученику.
- API-ключи и секреты хранятся вне репозитория.
- При удалении ученика удаляются связанные заметки и векторные представления.
- Для облачных моделей необходимо отдельно учитывать передачу данных внешнему провайдеру.

**Важно:** локальное хранение данных не означает полностью локальную обработку, если используется облачная LLM.

## 13. Дальнейшее направление

Долгосрочная цель — не создавать ещё одну полноценную CRM для репетиторов, а построить AI-слой, который может работать с данными из существующих систем.

Tutor RAG должен постепенно превратиться из самостоятельного инструмента для заметок в интегрируемого помощника, который:

- Получает информацию из разных источников.
- Сохраняет контекст обучения.
- Помогает готовиться к занятиям.
- Предлагает действия на основе истории ученика.
- Уменьшает количество ручной административной работы.

На ранних этапах приоритет отдаётся качеству retrieval, надёжности данных и практической пользе, а не количеству интеграций.
